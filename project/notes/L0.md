## DEVLOG note: tracer pcap rotation stalls on the Proxmox VM (AppArmor), 2026-11-10
Symptom: the tracer's rotating tcpdump (-G 300 -z gzip) stopped writing at its first rotation after pod start: the next pcap stayed 0 bytes, tcpdump PID 1 sat in state R, and the log said "compress_savefile: execlp(gzip, ...) failed: Permission denied". It happened twice (T7 after the UE restart, and again before R1), and adding -Z root did not help.
Cause (confirmed for the exec failure): Ubuntu 24.04 ships an AppArmor profile "tcpdump", attached by path to /usr/bin/tcpdump. It applies inside the container too, even in a privileged pod (the process is unconfined until the exec of tcpdump moves it into the attached profile). For -z the profile only allows exec of /{usr/,}bin/gzip and /{usr/,}bin/bzip2. In the nicolaka/netshoot image gzip is a symlink to /bin/busybox, and AppArmor matches the resolved target, so the kernel denied exec of /bin/busybox (audit: apparmor="DENIED" operation="exec" profile="tcpdump" name="/bin/busybox" requested_mask="x"). Every -z command failed the same way, even as root with full capabilities, so -Z root cannot help.
Why WSL2 never showed it: the WSL2 kernel has no AppArmor LSM, so tcpdump ran unconfined and busybox gzip exec worked.
Fix: no -z. tcpdump keeps its flags and filter, minus -z; the capture script's 60 s housekeeping loop gzips rotated files itself (compress to a hidden temp name, rename, remove the original), never touching the newest file (the one tcpdump has open), and retention also spares it. A liveness probe fails the container when the newest neoncore-*.pcap* is older than 120 s. The VM's AppArmor profile is untouched.
The PID 1 spin was not explained by any AppArmor denial (only exec denials were logged); see the live results below for whether it persists without -z.

## DEVLOG note (for docs-writer): why the tracer stalled twice
1) The pcap tracer ran `exec tcpdump ...` as the container's PID 1. phase6/capture.py starts a second per-scenario capture with `sh -c 'nohup tcpdump ... & echo $! > pid'` through kubectl exec. When that sh exits, the scenario tcpdump is orphaned and reparented to the pod's PID 1, i.e. the main tcpdump. When the scenario capture was stopped, PID 1 tcpdump went to state R at 100% CPU and stopped writing (reproduced on demand; the liveness probe then restarted it after about 4 minutes). It showed up as one restart in E3 suite 1 on R2.
2) The earlier stall had the same shape: with `-z gzip`, tcpdump forks a post-rotate child; the Ubuntu AppArmor profile "tcpdump" denied the exec of /bin/busybox (gzip is a busybox symlink), the child failed and exited, and PID 1 tcpdump spun. Dropping -z removed that trigger; the orphan problem remained for scenario captures.
3) Fix: `shareProcessNamespace: true` makes the pause container PID 1, which reaps orphans; tcpdump is now an ordinary process (pid 7). The exact code path inside tcpdump 4.99.6 that spins when a child of PID 1 exits was not identified; the trigger and the fix are proven by the repro. The compress-in-the-capture-loop design and the liveness probe stay as the safety net.
