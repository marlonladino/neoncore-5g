# L0 plan: lab on Proxmox, WSL2 retired, repo polish

## 1. Goal and roadmap mapping
The goal is to move the working NeonCore lab (Open5GS 2.8.0 + UERANSIM 3.3.0 on single-node K3s, Prometheus/Grafana, tracer, TUI, phase6 scenarios) **as it is** from WSL2 to one Proxmox VM that one command can rebuild. After that, WSL2 is retired and the repo is polished so it explains itself.

- **Roadmap weeks 1–2** ("Repo polish: description, topics, demo GIF of the TUI, a 'Roadmap' section in the README". Done when: "Repo explains itself in 30 seconds").
- The Proxmox migration is **not in the roadmap PDF**. It comes from `project/WORKFLOW.md` (stage L0, "Lab (Proxmox)").
- **Exit criteria (WORKFLOW.md, verbatim):** "All `neoncore`/`monitoring` pods healthy (`dbctl` Completed); UE ping via `uesimtun0`; 3 phase6 scenarios pass with valid pcaps; Grafana panels show data; one documented command rebuilds the lab from zero; nothing depends on WSL2/Windows; LAN exposure closed; repo explains itself in 30 s".

## 2. Out of scope
- Any lab improvement beyond the move. K3s flags, the Open5GS/UERANSIM/mongo/Prometheus/Grafana/kube-state-metrics image tags, NF configs, Grafana's anonymous admin and Mongo without auth all stay as they are ("migrate before improving"). The only exception is the tracer image digest pin in decision D9.
- Fault injection, datasets and any AI work (Stage 7+).
- Changes to `phase5/`/`phase6/` code. The hard-coded `REPO_ROOT=~/neoncore-5g` and `KUBECONFIG=~/.kube/config` already match the control machine, so they stay.
- Multi-node clusters, HA, LXC, and K3s or Docker on the Proxmox host.
- Proxmox datacenter or host settings: firewall, storage, network, users other than the NeonCore pool and token.
- Publishing the site. A push or GitHub metadata change happens only as an owner step (section 5, T15).
- The control machine itself. It stays outside Terraform state. The one exception is the gate change in D16, which only the owner can make.

## 4. Design
**Layout (all of it is lab-ops scope, except where noted):**
```
infra/
  lab.sh                 # one entry point: up | deploy | verify | start | stop | snapshot <name> | status
  lib/                   # pve_get.sh (pinned GETs, token via stdin), pin.sh (per-run leaf pin),
                         # plan_guard.py (fail-closed), approval_check.sh, hostkey.sh, wait helpers
  terraform/             # versions.tf (bpg/proxmox pinned exactly), main.tf, variables.tf, outputs.tf,
                         # .terraform.lock.hcl, terraform.tfvars.example (placeholders only)
  ansible/               # ansible.cfg, site.yml, roles: base, kernel, docker, k3s, firewall, upf_image
  tests/                 # bash/python tests for plan_guard, approval_check, pin, lab.sh args (no lab needed)
  .gitignore             # *.tfstate*, .terraform/, *.tfplan, crash.log, .terraform.tfstate.lock.info, inventory
start.sh, stop.sh        # thin wrappers: infra/lab.sh start|stop
evals/l0/redact.py       # evaluator-owned: the single redaction filter (S-B5), used by lab-ops too
```
**Documented command:** `scripts/labenv infra/lab.sh up`. It runs these steps:
1. Pin check
2. `terraform init/plan`
3. Plan guard
4. `apply`
5. Wait for cloud-init, then pin the SSH host key
6. `ansible-playbook`
7. Fetch kubeconfig
8. Deploy
9. Verify

It is idempotent: on a lab that's already up, the steps converge with no changes. "From zero" means no NeonCore VM exists. The prerequisites outside the command are written down: control-machine tools, a filled `.env.lab`, the pool/token/role that the owner creates once, and the template if D5 = (b).

**Approval check (security review S-B1):**
- Before any mutating subcommand (`up`, `deploy`, `start`, `stop`, `snapshot`), and inside `start.sh`/`stop.sh`, `lib/approval_check.sh` computes `sha256(project/plans/$(cat project/STAGE).md)`. It compares that with the hash recorded in that stage's approval file, the same comparison the gate does.
- A mismatch or a missing file means a refusal with a non-zero exit.
- `status` and `verify` are read-only and need no approval.
- The one exemption is the owner at a real terminal outside Claude Code (`[ -t 0 ] && [ -t 1 ]` and `CLAUDECODE` unset, the same test `approve.sh` uses). The owner can therefore run `start.sh` between stages.
- `infra/tests` cover a match, a mismatch, a missing file and an unknown stage.
- **Gate patterns:** the owner extends the gate's LAB list (T0, D16). If the owner declines, the fallback is stated in section 9.

**Terraform (`bpg/proxmox`):**
- One `proxmox_virtual_environment_vm` in the owner's pool, with the owner's VMID.
- VM name and hostname are the neutral, publishable `neoncore-lab` (S-B9).
- CPU type `x86-64-v3`, or `host` if A4 says only that works.
- Sizing from D6. Ballooning off, `agent.enabled=true` (qemu-guest-agent), and `on_boot` per D6.
- Cloud-init through the `initialization` block: `user_account` (dedicated user, the dedicated lab SSH public key, no password), `ip_config` static, and `dns`. **No snippets**, so the provider never needs SSH to the Proxmox host.
- The disk source follows D5: a pinned dated Ubuntu 24.04 cloud image with SHA-256, or a clone of the owner's template.
- Every site value (endpoint, node, VMID, pool, storage, bridge, IP/CIDR, gateway, DNS) arrives as `TF_VAR_*` from `.env.lab`. The repo holds placeholders only.
- The provider block has `insecure = false` written as a literal.
- **State is local, outside the repo** (`~/.local/state/neoncore/`, directory mode 700, set with `-backend-config`). A `git add -A` can never pick it up.

**TLS pinning (security review S-B3, S-B4):**
- **Per-run directory.** Every run creates a fresh `mktemp -d` (mode 700) under `~/.local/state/neoncore/`.
- **Fetch and pin.** `lib/pin.sh` fetches the node certificate with `openssl s_client`, unauthenticated, and writes **only the leaf** into that directory. It compares the file's SHA-256 with `PVE_TLS_FINGERPRINT`.
- **Re-hash before each exec.** `pin.sh` hashes the file again right before every `terraform` or `curl` exec, then exports `SSL_CERT_FILE=<leaf>` and `SSL_CERT_DIR=<empty mode-700 dir>`. That closes the check-then-use gap and the fallback to the system CA store.
- **On a mismatch,** `lab.sh` aborts. It never offers to re-pin, and the abort message never prints the expected or the actual fingerprint.
- **Environment aborts.** `lab.sh` aborts if `PROXMOX_VE_INSECURE`, any `PROXMOX_VE_SSH_*`, `TF_LOG` or `TF_LOG_PROVIDER` is set. If the provider ever asks for SSH to the host, lab-ops stops and reports.
- **Fail-only selftest.** `lab.sh status --selftest-bad-pin` flips one hex digit of the expected value and can only cause failure, for E10. No environment variable can replace the pin.
- **Token handling.** `pve_get.sh` uses `--cacert <leaf>` plus `--pinnedpubkey`. It passes the `Authorization: PVEAPIToken=…` header through stdin (`curl --config -`), never in argv. `lab.sh` never uses `set -x` and never prints environment variables.

**Plan guard (security review S-B2):**
- `lab.sh` runs `terraform plan -out <state dir>/<run>.tfplan` (mode 600). `plan_guard.py` checks `terraform show -json` of that file. `lab.sh` then runs `terraform apply <that file>`, never a fresh `apply`, and deletes the file afterwards.
- **The guard fails closed** on a JSON parse error, a missing plan file, an empty `resource_changes` together with a non-empty diff, an unknown action, or `"delete"` anywhere in `change.actions` (`["delete"]`, `["delete","create"]`, `["create","delete"]`).
- **Replace or delete confirmation.** These go ahead only after an interactive confirmation: `lab.sh` lists the affected resource addresses and reads the typed address from `/dev/tty`. It refuses with no TTY, with `CLAUDECODE` set, or if `NEONCORE_ALLOW_REPLACE` is present at all. That environment variable is gone from the design.
- **Tests.** `infra/tests` cover each guard case, malformed JSON and a missing plan file.
- **No destroy subcommand.** `terraform destroy` stays an owner-only command, typed by hand.

**SSH host key pinning (security review S-B6):**
- `ansible.cfg` sets `host_key_checking = True` and `StrictHostKeyChecking=yes`, with `UserKnownHostsFile=~/.local/state/neoncore/known_hosts` (mode 600). `StrictHostKeyChecking=no` is never used.
- After cloud-init, `lib/hostkey.sh` reads `/etc/ssh/ssh_host_ed25519_key.pub` through the pinned, authenticated API (guest agent `file-read`) and writes the known_hosts entry.
- On a rebuild, the entry is replaced only through that path. If A12 fails, D17 applies.

**Redaction (security review S-B5):**
- `evals/l0/redact.py` is owned by the evaluator, so builders can't weaken it. lab-ops and the evaluator pipe every write under `project/notes/L0.md` and `project/reports/L0/**` through it.
- It works in four steps:
  1. **Replace site values in-process:** the endpoint host, every `TF_VAR_*`, `LAB_ADMIN_CIDR`, the fingerprint, and the VM and host names, read from the environment.
  2. **Redact by structure:** `nodeName`, `hostIP`, `hostname`, kube context and cluster names, node `InternalIP`, and `instance` labels that carry the node address.
  3. **Replace stray IPv4:** any address outside the documented lab ranges (pod/service CIDRs, the UE pool, addresses already in the phase manifests) becomes `<ip>`.
  4. **Fail closed:** after writing, it re-scans the file for each sensitive value and any non-allowlisted RFC1918 address. On a hit, it deletes the file and exits non-zero.
- Raw output goes only to the state directory or the session scratchpad, never into the repo first.
- Inside WSL2 (B, D14), `capture_baseline.sh` applies steps 2–4 and also adds the WSL2 hostname, which can be the Windows computer name, to the step 1 values.

**Ansible (builtin modules only, no Galaxy; no `-v`, no `--diff`; `no_log: true` on every task that touches the kubeconfig or keys):**
- **base:** an sshd drop-in at `/etc/ssh/sshd_config.d/00-neoncore.conf`, read before cloud-init's `50-cloud-init.conf`, with `PasswordAuthentication no`, `KbdInteractiveAuthentication no`, `PermitRootLogin no` and `AllowUsers <lab user>`. `sshd -T` output is recorded. qemu-guest-agent and chrony/timesyncd are active.
- **kernel:** this role ports `setup/enable-sctp.sh` and `prepare-k3s-kernel-modules.sh` (`sctp`, `iptable_nat`, `macvlan`, `ipvlan`, persisted in `/etc/modules-load.d/`). It installs `linux-modules-extra` if A7 needs it. It does **not** modprobe `nf_conntrack_proto_sctp`: on this kernel that's built into `nf_conntrack`, so the step would fail on a healthy VM. The headless Services stay unchanged (telco TA13).
- **docker:** ports `setup/install-docker.sh`, using the Docker apt repo with its GPG key.
- **k3s:** `INSTALL_K3S_VERSION=<D8>` and `INSTALL_K3S_EXEC="--docker --disable=traefik --disable=servicelb"`, the same flags as today. The play then fetches `/etc/rancher/k3s/k3s.yaml` and rewrites `server:` to the VM address. The kubeconfig goes to `~/.kube/config` on the control machine with mode 600. If the gate blocks that write, the owner runs the one fetch line.
- **firewall:** see LAN exposure below.
- **upf_image:** copies `phase2/upf-metrics-patch/` to the VM and runs `docker build -t neoncore-upf:2.8.0-metrics`. K3s with `--docker` shares the Docker image store, so `imagePullPolicy: IfNotPresent` finds the image.
- When Ansible covers all five scripts in `setup/`, they are removed (`git rm`, reversible). The README points to Ansible.

**UPF image:** rebuilt on the VM from the committed Dockerfile and patch. Same tag, same Open5GS v2.8.0 source and patch, same `gradiant/open5gs:2.8.0` base. The Dockerfile's `apt-get upgrade` means the build is not bit-identical; that's acceptable and gets recorded.
- **Verification:** `open5gs-upfd -v` reports 2.8.0, and the N3 GTP counters (`fivegs_ep_n3_gtp_indatapktn3upf`) rise during the ping test.

**Deploy (`lab.sh deploy`, from the control machine):**
- Applies `phase1/multus-helmchart.yaml` unchanged, then the manifests in the README order: phase2 00–02, wait for mongo, 03–05, then phase3 and phase4. `phase1/test-macvlan-nad.yaml` is never applied.
- Then it waits for UPF Ready, **restarts SMF, waits, then restarts UE** (the DEVLOG order UPF → SMF → UE).
- **Tracer liveness check:** the newest pcap must grow within 60 s. If it doesn't, the tracer pod is restarted (never by deleting a pcap that's still open).
- **`start.sh`/`stop.sh`** keep their meaning, but run on Proxmox: VM start/shutdown through the API, then workload scale up/down. After **every** VM boot, including the T10 rollback boot, `start.sh` runs the same UPF → SMF → UE order, because pod IPs can change on boot (telco TA12).

**LAN exposure (security review S-B7):**
- **Table and chain:** an nftables table `inet neoncore_guard` on the VM, in its own file holding only that table. It's re-created with `destroy table` plus a fresh definition (nft 1.0.9 on 24.04).
  - A `prerouting` filter chain at priority −150 runs after conntrack and **before** the kube-proxy/Docker DNAT at −100, so NodePorts can't bypass it the way they bypass `ufw` INPUT rules.
  - It's loaded by a dedicated oneshot unit with `Before=network-pre.target docker.service k3s.service`.
  - Never `flush ruleset`, and never restart `nftables.service` on a live node: that would wipe the Docker, kube-proxy and flannel tables.
- **Rules,** on the LAN NIC only:
  1. `ct state invalid drop`.
  2. Accept established/related traffic.
  3. Accept new TCP to 22, 6443, 30030 and 30090 from `LAB_ADMIN_CIDR` (D7).
  4. Drop all other new inbound traffic, with a family-agnostic final drop (IPv4 and IPv6) that has a `counter`. This covers kubelet 10250, flannel 8472/udp, other NodePorts and everything else.
- Pod, loopback and egress traffic aren't touched.
- **Auto-revert:**
  - Before applying, arm `systemd-run --on-active=120 nft delete table inet neoncore_guard`.
  - Cancel the revert only after a **new** SSH connection succeeds. Enable the persistent unit only after that confirmation.
  - If the revert fires, the Ansible run fails (non-zero), and `lab.sh verify` fails while the table is absent.
  - The key-only user has no console password, so the recovery path is the `l0-base` snapshot, or a rebuild if the first run locks out before `l0-base` exists.

**Snapshots:**
- `l0-base`: after base, kernel and firewall are verified, before K3s.
- `golden-l0`: once everything is green, taken with the VM cleanly shut down by `stop.sh` so it's consistent, then the VM is restarted and checked again.

**Alternatives considered:**
| Choice | Lost because |
|---|---|
| Transfer `neoncore-upf` with `docker save` from WSL2 | The rebuild would depend on WSL2 forever, which breaks "nothing depends on WSL2" |
| Push the UPF image to a registry | A public registry means publishing. A local registry adds a component and a port |
| Adapt the `setup/` scripts over SSH | They assume an interactive TTY with sudo and WSL2 paths, and they aren't idempotent |
| Cloud-init `runcmd` only | No idempotent re-run; the K3s install and UPF build in user-data are hard to debug |
| Proxmox VM firewall | It only takes effect when the **datacenter** firewall is on, and that's a host-wide change to off-limits settings |
| `ufw` in the VM | NodePort traffic is DNATed and goes through FORWARD, not INPUT, so ufw doesn't close 30030/30090 |
| The standard `/etc/nftables.conf` | It starts with `flush ruleset`, which wipes the K3s/Docker tables on any reload |
| SSH-only exposure with tunnels for 6443 and NodePorts | Smallest surface, but every TUI/kubectl session depends on a tunnel. Offered as D7 option (b) |
| Snippet-based cloud-init user-data | Needs SSH as root to the Proxmox host |
| Terraform state in the repo with `.gitignore` | One mistaken `git add -f` leaks VM config. Outside the repo is safer |
| An environment override for replaces | Any agent could set it (security S-B2). Replaced by a TTY confirmation |
| SSH trust on first use | A LAN impersonator could capture the kubeconfig (security S-B6). Only a fallback, D17 |

#### 3. Valid pcap (used by E3 and B3; `evals/l0/pcap_check.py`)
**Tools:** tshark is run with `-o nas-5gs.null_decipher:TRUE`, because Open5GS uses NEA0, so the integrity-protected NAS messages can be decoded. If the installed tshark doesn't know that preference, the checker fails loudly and doesn't guess. The B pcaps and the Proxmox pcaps go through the same tshark version on the control machine.
- **Field names (amended per telco review TB4):** before the build starts (T3b), the evaluator runs `tshark -G fields` and `tshark -G defaultprefs` on the pinned tshark and confirms that every field and preference the checker uses exists (including the PFCP UE IP Address / F-SEID / SEID fields and the NAS PDU-address field from the tie rule). `pcap_check.py` repeats that check at every start and fails loudly on a missing name.
- **Duplicates (amended per telco review TA4):** `tcpdump -i any` sees every pod-to-pod frame twice (veth and cni0). Frames are de-duplicated (first frame kept, matched by IP ID plus SCTP TSN) before any count or any cited frame number.

A scenario pcap is **valid** only if all of these hold:
- **V0 Readable:**
  - The local file exists, its size is over 24 bytes, and its sha256 is recorded.
  - `capinfos -c` reports at least 1 packet.
  - `tshark -r` exits 0 with no "cut short" or "appears to be damaged" warning.
- **V1 Protocols present:** at least one `ngap` frame (SCTP) and at least one `nas-5gs` frame.
- **V2 Tied to this run:** a Registration request (5GMM type 0x41) whose SUCI MSIN (`nas-5gs.mm.suci.msin`) equals the run's suite MSISDN. The responses below must be on the same `ngap.RAN_UE_NGAP_ID` as that request. This makes sure the evidence comes from the scenario UE, not the background `ue` pod.
  - **initial-registration:** Registration accept (0x42) and Registration complete (0x43).
    - [B] PDU session establishment request/accept (5GSM 0xc1/0xc2).
    - [B] PFCP Session Establishment Request/Response (`pfcp.msg_type` 50/51), tied by the PFCP tie rule below.
    - A PDU session establishment reject (0xc3) for the run UE makes the pcap invalid. Its 5GSM cause is recorded (amended per telco review TA6).
  - **registration-reject (amended per telco review TB2):** Registration reject (0x44) for the run UE with `nas-5gs.mm.5gmm_cause == 7` (5GS services not allowed; reference: `traces/rogue-ue-reject.pcap`, and DEVLOG). No Registration accept for that UE. The cause must also equal B's (C2). If B shows a cause other than 7, B is recorded as degraded, and Proxmox must still show 7.
  - **deregistration (amended per telco review TB3):** 0x41, 0x42 and 0x43 as above, then a UE-originating Deregistration request (0x45) with `nas-5gs.mm.switch_off == 0`, **followed by a Deregistration accept (0x46) on the same UE (required, not [B])**. If switch_off is 1, the pcap is invalid (the scenario did not do what its label says).
    - [B] NGAP UEContextRelease (procedureCode 41).
    - [B] PFCP Session Deletion (54/55), tied by the PFCP tie rule below.
  - **PFCP tie rule (amended per telco review TB4):** a PFCP Session Establishment Request (50) belongs to the run UE if a UE IP Address IE in it equals the IPv4 PDU address in that UE's PDU session establishment accept (0xc2, on the run's RAN_UE_NGAP_ID). Its Response (51) is matched by PFCP sequence number. A Session Deletion Request/Response (54/55) belongs to the run UE if its header SEID equals the F-SEID that the Establishment Request/Response pair for that UE assigned. If the PDU address can't be read from the pcap, the PFCP items are reported as 'untied' and do not count toward C2.
- **V3 Default for missing B:** if B is missing, the [B] items are reported but not required. GTP-U is not required in scenario pcaps, because the scenarios carry no user data. It is checked in E2.

A run with an invalid pcap but a runner PASS counts as **not valid** (the WORKFLOW rule). It may be retried after a tracer restart. Retries are limited by E3.

## 9. Security risks
- **Gate blind spot (security review S-B1).** Today the gate doesn't restrict `infra/lab.sh`, `scripts/labenv`, `start.sh` or `stop.sh` by actor or by approval. `lab.sh` also runs `terraform apply`, `ansible-playbook`, SSH and Proxmox POSTs inside subprocesses, so the `ask` rule on `terraform apply` never fires. The reviewer showed that evaluator, docs-writer, lead and blog-writer can all start these.
  - Control 1 (always on): `lab.sh`, `start.sh` and `stop.sh` refuse mutating subcommands unless the current stage plan's hash matches its approval. The only exemption is the owner at a real TTY outside Claude Code.
  - Control 2 (D16, owner): gate LAB patterns make these lab-ops-only.
  - Further controls: the fail-closed plan guard with a TTY confirmation for replaces and deletes, no destroy subcommand, and owner-approved rollbacks and snapshot deletes.
  - **If the owner declines D16:** any agent can run `lab.sh`, `start.sh` and `stop.sh`, and control 1 is the only control. `docs/agent-gate.md` gets a line saying so (T11).
- **Token scope.**
  - Privilege-separated token of a dedicated `neoncore@pve` user, with the ACL limited to the pool, storage and bridge. Stored only in `.env.lab`.
  - Never in argv: curl reads the header from stdin. Never in Terraform state (it's passed by env). Never in logs: no `set -x`, `TF_LOG*` aborts, and Ansible runs without `-v`/`--diff` and with `no_log`. Never in the E10 trace (count 0 is checked).
  - On PVE 8, `VM.Monitor` (needed for the guest-agent host-key read) includes guest-exec, which is root in the VM.
- **TLS.**
  - A fresh per-run leaf file is re-hashed before each exec. `SSL_CERT_DIR` points at an empty dir, so the system CA store can't be used.
  - `insecure = false` is a literal, and `PROXMOX_VE_INSECURE`/`PROXMOX_VE_SSH_*` abort the run.
  - There's no re-pin path, and fingerprints are never printed.
  - The negative tests include a nonexistent cert file.
- **SSH.**
  - Key-only dedicated user with a dedicated lab key. sshd drop-in `00-neoncore.conf`, `AllowUsers`, no root login, port 22 only from the allowlist. Passwordless sudo, as WORKFLOW allows.
  - Host key pinned through the guest agent and `StrictHostKeyChecking=yes`. TOFU only by D17, with its risk recorded here if chosen.
- **LAN.**
  - Grafana with anonymous Admin, Prometheus without auth, the K3s API, kubelet and the privileged hostNetwork tracer are reachable only from `LAB_ADMIN_CIDR`. The nftables guard runs before DNAT, has its own table and unit, never flushes the ruleset, and its final drop also covers IPv6.
  - Leftover risk: anything on the allowlisted host can use these services, agents included.
- **UE egress.** The UPF NATs UE traffic out of the VM, so a UE could reach LAN hosts. This is unchanged from WSL2 and not closed in L0. It's flagged for the Stage 7 plan, which runs faults.
- **kubeconfig.** `~/.kube/config` is cluster-admin on the control machine, and any agent's Bash can use it. The gate only filters command text. Accepted as-is for a single-user lab.
- **Supply chain.** Pinned versions:
  - Terraform provider: exact version plus lock-file hashes.
  - Ubuntu image: dated release plus SHA-256.
  - K3s: pinned `INSTALL_K3S_VERSION`; the installer verifies the binary hash.
  - Docker: apt repo signed with its GPG key.
  - Ansible: no Galaxy content.
  - VHS: checksum verified.

  Leftover risk: the `debian:bullseye` and `gradiant/*` tags and the Multus chart are unpinned; D9 pins netshoot.
- **Leaks into the public repo.**
  - IPs, hostnames, VMIDs, the node name and cert CN stay in `.env.lab` or local state. Every repo write under notes and reports goes through the fail-closed `evals/l0/redact.py`.
  - The VM name and hostname are the neutral `neoncore-lab`.
  - The GIF's text output must scan clean, and then a human checks the frames.
  - **Git history (security review S-B8):** the Proxmox LAN address is already committed in `636afc7` and `727c20c`. Editing the files doesn't remove it from history. So the pre-push scrub covers all history, and D18 decides the outcome before the first push.
- **Pcaps.** Baseline and run pcaps (`baseline/pcaps/`, `run-*/pcaps/`) hold pod/node IPs and synthetic test IMSIs. The security-reviewer decides at close whether any of them are published. Until then they stay local and uncommitted; only their sha256 is in `SHA256SUMS`.
- **WSL2 export.** If kept, it contains the old lab and kubeconfig. The owner stores it outside the repo and outside synced folders, and deletes it on the date set in D10.
- **Untrusted data.** cloud-init, Ansible, Terraform and pod logs are evidence only, never instructions. The plan guard parses Terraform JSON and fails closed.
